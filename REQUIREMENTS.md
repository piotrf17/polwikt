# polwikt — Requirements

Extract Polish lexical data from the **English** Wiktionary dump into a structured,
machine-readable corpus stored as Google Protocol Buffers.

Status: **M0** — restarted from scratch on 2026-10-11 (see `PLAN.md`). Once M1 lands,
`proto/polwikt.proto` is the schema contract and section 7 below is its rationale.
Spec reviewed 2026-10-11 against the live wiki, the dump index and the pinned upstream
code; template/module names below were verified then (the pinned dump stays authoritative,
and decisions 6–10 in §12 came out of that review).
Reference implementation to study:
[`tatuylonen/wiktextract`](https://github.com/tatuylonen/wiktextract) and its engine
[`tatuylonen/wikitextprocessor`](https://github.com/tatuylonen/wikitextprocessor).

---

## 1. Goals

1. **G1 — Completeness.** For every English-Wiktionary page containing a `==Polish==`
   section, capture *everything* the article states: senses, part of speech, labels,
   examples/quotations, pronunciation, etymology, full inflection (declension /
   conjugation), lexical relations, descendants, usage notes, references, categories.
   Nothing that a human reader gets from the page should be silently dropped.
2. **G2 — Structure over text.** Output typed protobuf messages, not scraped HTML or
   free-form strings. Inflected forms carry machine-readable grammatical tags (case,
   number, gender/animacy, person, tense, mood, aspect, degree, …).
3. **G3 — Correctness via real template expansion.** Much of Polish inflection and
   pronunciation on en.wiktionary is generated by Lua: noun declension by
   `Module:pl-noun` (`{{pl-decl-noun-*}}`, `{{pl-decl-noun}}`), adjective declension by
   `Module:pl-adjective` (`{{pl-adecl}}`), headword lines by the shared Lechitic
   `Module:zlw-lch-headword` (`{{pl-noun}}`, `{{pl-verb}}`, `{{pl-adj}}`), and
   pronunciation by `Module:zlw-lch-IPA` (`{{pl-pr}}`). Verb conjugation is mostly
   plain-wikitext template families (`{{pl-conj-ai}}`, `{{pl-conj-ap}}` and their
   subclasses). Regex scraping cannot recover any of this; the pipeline must actually
   expand templates and Scribunto modules.
4. **G4 — Fast iteration.** The expensive parts (dump scan, template/module closure)
   run once and are cached; the extraction logic can be re-run over a small Polish-only
   subset in minutes, not hours.
5. **G5 — Reproducibility.** Same dump + same code ⇒ byte-identical output. Every
   output record is traceable to a dump date, page id and revision id.

### Non-goals (v1)

- Other languages (the design must not *preclude* them, but only `pl` is extracted).
- Rendering wikitext to HTML.
- Editing or writing back to Wiktionary.
- A query server / API. Output is files; consumers are separate tools.
- Data from the Polish-language Wiktionary (pl.wiktionary). English Wiktionary only.

## 2. Input

- **Source:** the recombined single file `enwiktionary-<YYYYMMDD>-pages-articles.xml.bz2`
  from `https://dumps.wikimedia.org/enwiktionary/` (~1.65 GB for 20261001). Not the
  multistream variant and not the split `pages-articles1.xml-p…` parts: the pin names one
  file and one sha1, and `lbzcat` already decompresses a single-stream bz2 in parallel, so
  multistream buys nothing here.
- The pipeline must accept a **local path** to an already-downloaded dump; downloading
  is an optional convenience subcommand, never implicit.
- **R2.1** Verify the dump against the published `*-sha1sums.txt` before use; refuse to
  proceed on mismatch unless `--no-verify`.
  - **Send a descriptive `User-Agent`.** `dumps.wikimedia.org` answers **403** to requests
    without one — verified. Use `polwikt/<version> (<contact>)` per Wikimedia's UA policy.
  - Prefer `lbzcat` over `bzcat` for decompression when present (`wikitextprocessor`
    auto-detects it); fall back to Python's `bz2` module otherwise.
- **R2.1a — One pinned dump for development.** The project pins a single dump date, held
  in `polwikt.toml` as `[dump].date` + `[dump].sha1`, and every dev run, golden test and
  `stats.json` comparison uses it. Tracking `latest` would make R8.3's regression diff
  meaningless — a count change could be our bug or a month of Wiktionary edits, and we
  could not tell which. The pin is set to the newest complete dump at first fetch and
  recorded in the file. Wikimedia publishes enwiktionary **monthly, on the 1st**; on
  2026-10-11 the index held 20260101–20261001, so retention is roughly ten months — re-pin
  before the pinned one expires, and keep a local copy regardless. The candidate at
  M2 is `20261001` (sha1 `f9ed426c69c6b21d026613bd0f200c2aaa1145e9`).
  - Moving the pin is a deliberate commit: bump `polwikt.toml`, re-run P1–P4, and review
    the `stats.json` diff *as part of that commit*, so Wiktionary's churn and our code
    changes never land in the same diff.
  - `--dump <path>` still overrides for one-off runs; a run against an unpinned dump is
    labelled as such in the output `Corpus` metadata (R7.4).
- **R2.2** Namespaces that must be read from the dump:
  | ns | name | why |
  |----|------|-----|
  | 0 | (main) | the entries themselves — **kept only when they have a `==Polish==` heading** (R3.2) |
  | 10 | `Template:` | template expansion |
  | 828 | `Module:` | Scribunto Lua modules |
  | 118 | `Reconstruction:` | Proto-Slavic etyma referenced by Polish etymologies |
  | 100 | `Appendix:` | glossary/label targets, some inflection appendices |
  | 110 | `Thesaurus:` | sense-level thesaurus links |
  Categories (ns 14) are *not* needed as pages; category membership is recorded from
  the expansion side. Pages in any other namespace (Citations 114, Wiktionary 4,
  Rhymes 106, …) are not stored — only their titles, in `all_titles` (R3.2a).
- **R2.3** Handle redirects (`<redirect title="…"/>`) — record them, resolve template
  and link redirects during expansion.
- **R2.4** The dump must never be fully decompressed to disk as a requirement; stream it.

## 3. Pipeline architecture

Multi-pass, each pass persisting an artifact so later passes can be re-run alone.

```
 enwiktionary-*.xml.bz2
        │
   [P1] scan & filter ──────────────►  pages.sqlite        (ns-0 pages with a
        │                                                    ==Polish== heading, ONLY;
        │                                                    + all Template:/Module:/
        │                                                    Reconstruction:/Appendix:/
        │                                                    Thesaurus: pages
        │                                                    + all_titles: ns-0 titles,
        │                                                      no text)
  ([P2] dependency closure ─────────►  subset.sqlite       DEFERRED, see R3.6)
        │
   [P3] extract  (parallel workers) ─►  words-*.pb.zst     (protobuf shards; reads
        │                                                    pages.sqlite directly)
        │                              + unhandled.jsonl, stats.json
   [P4] link & finalize ─────────────►  polwikt.pb.zst     (canonical corpus)
                                        + index.sqlite (title → shard, offset)
```

### P1 — Dump scan and page store
- **R3.1** Single streaming pass over the XML producing a SQLite store that
  `wikitextprocessor` reads **directly** via `Wtp(db_path=…)`. That means writing its own
  `pages` table — `(title, namespace_id, redirect_to, need_pre_expand, body, model)`,
  keyed by `(title, namespace_id)`, body as plain `TEXT` — exactly as upstream creates it
  (verified at the pinned SHA; it has no page id, no revision id and no compression).
  What upstream lacks lives in our own tables in the same file: `page_meta(title, ns,
  page_id, revision_id)` for G5 traceability, `all_titles` (R3.2a), and `scan_meta` (dump
  fingerprint, predicate fingerprint, counters — R3.4/R3.5). Our tables are additive; we
  never alter upstream's schema, so an upstream bump can't silently break the handoff.
- **R3.2 — ns-0 filtering.** From namespace 0, **store only pages that contain a
  `==Polish==` level-2 heading**; every other ns-0 page is discarded during the scan and
  never written. This is the whole point of P1: turn a ~10M-page dump into a store two
  orders of magnitude smaller, so that every subsequent pass is cheap.
  - Detection is by **heading**, not substring: match `^==\s*Polish\s*==\s*$` on a line
    (allowing `== Polish ==` spacing). A page merely *mentioning* Polish — in a
    translation table, a `{{also|…}}` hatnote, an etymology of an English word — is not
    a Polish entry and must be dropped.
  - Consequence: `{{l|pl|…}}`, translation and cognate links from Polish entries may
    point at ns-0 pages that are no longer in the store. That is expected; such links
    are stored as **titles**, and the pipeline must never try to read the target page's
    content.
- **R3.2a — Title-only table for existence checks.** Retain a lightweight `all_titles`
  table with `(page_id, ns, title, redirect_target)` for *every* page in the dump, with
  **no wikitext**. Some Lua modules and `{{#ifexist:}}` calls test whether a page exists
  (red-link detection, `mw.title.new(…).exists`); without this, expansion would silently
  produce wrong output for those templates. Cost is a few hundred MB; dropping it is not
  worth the risk.
  - Upstream answers existence (`page_exists`, `{{#ifexist:}}`, `.exists`) from its
    `pages` table alone, so pruned titles would read as red links. The expansion layer
    must route existence checks through `all_titles` (a `Wtp` override, M4).
  - Corollary: `mw.title.new(…):getContent()` on a non-retained page cannot be served.
    Upstream would return nil — i.e. "page does not exist", silently wrong. It must raise
    a recorded, counted error instead, so we learn if any Polish-reachable module
    actually depends on it.
- **R3.3** Non-ns-0 namespaces (Template, Module, Reconstruction, Appendix, Thesaurus per
  R2.2) are stored **unfiltered** in P1 — which templates are reachable is not knowable
  during a single streaming pass, and that pruning is P2's job.
- **R3.4** Idempotent and resumable: if the store exists and its recorded dump
  fingerprint matches, P1 is skipped. The store records the filter predicate used, so
  changing the Polish-detection rule invalidates it.
- **R3.5** The scan must report how many ns-0 pages it read vs. kept, so a broken
  predicate (keeping ~0 or keeping ~everything) is obvious immediately.
- Expected magnitudes (sanity checks, not hard contracts): page ids in the 20261001 dump
  run to ~12.2M. On 2026-10-11 `Category:Polish lemmas` held ~101k pages and
  `Category:Polish non-lemma forms` ~80k, so P1 should keep **~1.5–2×10^5** ns-0 pages
  (some pages are in both). Template and Module counts are measured at M2, not guessed.

### P2 — Template / module closure (DEFERRED)

**Deferred by decision 6 (§12).** P1 already prunes ns-0 to Polish pages, Lua `require`
targets are computed at runtime so any static closure needs a fallback to the full store
anyway, and `--pages`/`--limit` give the fast iteration loop G4 asks for. P3 therefore
reads `pages.sqlite` directly. R3.6–R3.8 are kept as the spec for P2 should it come back;
the trigger is M2 measuring `pages.sqlite` too large to stay in page cache on the dev box.

- **R3.8a — Record what expansion actually touches.** The expansion layer logs every
  Template/Module page it loads (per page, de-duplicated). That empirical closure builds
  the golden-test store snapshot (R8.1a), and it is the data a revived P2 would start
  from.
- **R3.6** Starting from the Polish pages, compute the **transitive closure** of every
  `Template:` and `Module:` they can reach: `{{tpl}}` calls, `{{#invoke:Mod|fn}}`,
  Lua `require("Module:…")` and `mw.loadData("Module:…")`, plus redirects.
- **R3.7** Because Lua `require` targets can be computed at runtime, the closure must be
  *over-approximate*: include all modules matching the Polish/Slavic families
  (`Module:pl-*`, `Module:sla-*`, `Module:languages/*`, `Module:scripts/*`,
  `Module:utilities`, `Module:table`, `Module:string*`, `Module:parameters`, …), and
  fall back to the full P1 store on a miss rather than failing — P1 keeps every
  Template/Module page (R3.3), so the fallback always succeeds for them. A miss must be
  logged, since a systematic one means the closure walker is missing a call form.
  There is no such fallback for ns-0 pages: those are pruned in P1 by design, and a
  module reaching for one is the error case described in R3.2a.
- **R3.8** The output subset must be small enough to fit comfortably in RAM/SSD cache so
  that P3 iterations are fast (target: < 2 GB).

### P3 — Extraction
- **R3.9** For each Polish page: expand templates → parse to a node tree → walk the
  section structure → emit one `Word` message per page.
- **R3.10** Parallel across processes with a configurable `--jobs` (default: CPU count,
  capped so `jobs × R9.3 budget` fits in available memory). Workers are stateless apart
  from a read-only handle to the page store. The reference implementation needs ~5 GB per
  worker for all of English; we must fit R9.3.
- **R3.11** Deterministic output ordering (sort by page id) regardless of `--jobs`.
- **R3.12** A single page that raises must not kill the run: catch, log to
  `errors.jsonl` with the page title and traceback, continue. A configurable
  `--max-error-rate` aborts the run if exceeded (default 1%).

### P4 — Link and finalize
- **R3.13** Resolve `form_of` / `alt_of` references from inflected-form entries to their
  lemma page, and (where the lemma has multiple etymologies/POS) to the specific entry.
- **R3.13a — Fold non-lemma entries into the lemma; do not emit them.** An inflected-form
  entry (`kotów` = "genitive plural of *kot*") produces **no `Word` record of its own**.
  Its content is merged into the lemma's paradigm and then discarded. The corpus contains
  lemmas only.
  - The rule applies **per POS entry, not per page**. Many Polish page titles are both a
    lemma and an inflected form of something else: `bez` is a preposition and noun lemma
    *and* genitive plural of *beza*; `mieć` is a verb lemma *and* an imperative of
    *mieść*. Drop the non-lemma entries; keep the page if any lemma entry survives; drop
    the page only when nothing does. Conversely `mamy` has two entries, both form-of
    (*mieć* 1pl present, *mama* gen sg / nom-acc-voc pl): it yields no record and folds
    into **two** lemmas.
  - "Non-lemma" means the entry's senses are *all* **inflectional** form-of senses
    (`{{inflection of}}` / its alias `{{infl of}}`, `{{plural of}}`,
    `{{superlative of}}`, …). An entry with even one substantive gloss is a lemma entry
    and is kept whole. Non-inflectional "of" templates — `{{syn of}}`, `{{alt form}}`,
    `{{alternative spelling of}}`, `{{dim of}}` — do **not** trigger folding: those
    entries are records of their own, with the link kept as a `Relation`/`FormOf`.
  - **Participle entries are not folded** (decision 10, §12). `===Participle===` entries
    carry their own adjectival declension tables and often their own senses; folding
    them into a single verb `Form` would lose that. They stay records, linked to the verb
    via `form_of`, and the verb's paradigm `Form` points at them. Indeclinable adverbial
    participles (`-ąc`, `-wszy`) have no paradigm and fold normally.
  - **Fold, don't just delete.** Before dropping, transfer anything the lemma's own
    paradigm does not already carry: mark the matching `Form` as attested by a dedicated
    page, add forms the generated table missed, and attach the form page's pronunciation
    to that `Form`. Sense-level content on a pure form-of entry (labels such as
    *archaic*, *dialectal*) rides along on the `Form`'s tags.
  - **R3.13b** Keep the lookup path alive: `index.sqlite` maps **every** folded surface
    form title → `(lemma title, entry id, tags)`, so a consumer resolving `kotów` still
    lands on `kot`. This mapping is index-only; it is not a protobuf record.
  - **R3.13c** A form-of entry whose lemma cannot be resolved (target page absent,
    ambiguous, or the link is broken) must **not** be silently dropped — count it, log it
    to `unresolved_forms.jsonl`, and expose the count in `stats.json`. This is the metric
    that tells us whether folding is losing data.
- **R3.14** Build derived cross-references: verb **aspect pairs** (imperfective ↔
  perfective, from the aspect-partner arguments of `{{pl-verb}}` and from the *Related
  terms* section), frequentatives (`{{pl-verb|…|freq=}}`), diminutive/augmentative
  chains (`{{pl-noun|…|dim=}}`), comparative ↔ positive adjectives (`{{pl-adj}}`).
- **R3.15** Emit the canonical sharded corpus plus a `title → (shard, offset)` index.
- **R3.16** Emit `stats.json`: counts by POS, senses, forms, pages with/without
  inflection, top unhandled templates by frequency. This is the primary quality signal.

## 4. Template expansion (the hard part)

- **R4.1** **Build on `wikitextprocessor`.** Do not reimplement the MediaWiki parser or
  the Scribunto sandbox. It provides the SQLite page db, `expand()`, `parse()` →
  `WikiNode` tree, parser functions, and a Lua sandbox (via `lupa`) with the `mw.*` API
  emulated. Reimplementing this is a multi-year effort and is the reason wiktextract
  exists.
- **R4.2** The pipeline must still own the *policy* of what to expand:
  - **Expand fully** in inflection sections (`{{pl-decl-noun-*}}`, `{{pl-conj-*}}`) —
    the tables are the payload.
  - **Capture as structured template calls** where the call itself is the data:
    `{{lb|pl|…}}` labels, `{{ux|pl|…}}` / `{{uxi|pl|…}}` usage examples, `{{coi|pl|…}}`
    collocations, `{{+obj|pl|…}}` government, inline nyms (`{{syn|pl|…}}`,
    `{{ant|pl|…}}`), `{{inh|pl|…}}` / `{{inh+}}` / `{{bor|pl|…}}` / `{{der|pl|…}}` /
    `{{etymon}}` etymology templates, `{{IPA|pl|…}}`, `{{pl-pr}}`, `{{inflection of|pl|…}}`,
    `{{col|pl|…}}` term lists. "Capture" means the typed fields come from the call's
    arguments, never from scraping its rendering; the call is still *rendered* where it
    contributes visible text, because the plain-text view (R7.6a) needs it.
  - **Both** for headword lines (`{{pl-noun}}`, `{{pl-verb}}`, `{{pl-adj}}`): keep the
    raw call *and* the expanded gender/aspect/form annotations.
  - Template aliases and redirects are resolved before policy lookup (`{{infl of}}` →
    `{{inflection of}}`, `{{tlb}}` → `{{term-label}}`), so the policy names the canonical
    template once.
  - **R4.2.1** Retain the raw `{name, args}` of every inflection/headword/etymology
    template in the proto (`*_templates` fields), as wiktextract does. This is the
    escape hatch when our table parsing is wrong.
- **R4.3** `#invoke` of Polish modules must actually execute. If Lua fails for a page,
  degrade gracefully: emit the entry without the inflection table, record the failure.
- **R4.4** Handle: parser functions (`#if`, `#ifeq`, `#switch`, `#expr`, `#invoke`,
  `#categorytree`), template parameters with defaults (`{{{1|}}}`), magic words
  (`{{PAGENAME}}`, `{{SUBPAGENAME}}`, `{{NAMESPACE}}`), `<nowiki>`, `<ref>`, HTML
  comments, `{{DISPLAYTITLE}}`, and template redirects.
- **R4.5** Expansion must be **hermetic**: no network access at runtime, no wall-clock or
  random dependence (so G5 holds). Lua execution is sandboxed and time-limited per page.
  - **Upstream is not hermetic by default.** At the pinned SHA, `wikitextprocessor`
    implements `mw.wikibase.*` and several label/description lookups with **live HTTP
    queries to wikidata.org**. Those entry points must be stubbed out by the expansion
    layer; each call is counted (`stats.json`) and returns the "no data" answer, so a
    module that depends on Wikidata degrades visibly instead of reaching the network.
- **R4.6** Every template name encountered and *not* handled by a rule must be counted in
  `unhandled.jsonl` with an example page. This list drives the work backlog.

## 5. Article structure to capture

English-Wiktionary Polish sections follow this nesting:

```
==Polish==                       (L2, the language)
  ===Alternative forms===                        (language-level, above etymologies)
  ===Pronunciation===                            (above the etymologies when shared)
  ===Etymology===  / ===Etymology 1===          (may repeat; splits the entry)
    ===Noun===  / Verb / Adjective / …           (POS, L3 or L4; may repeat — iść has
                                                  two ===Verb=== in one etymology)
      headword line   {{pl-noun|m-in|dim=…}}
      # sense gloss   {{lb|pl|colloquial}} … {{gl|…}} {{+obj|pl|…}}
      #: usage example  {{uxi|pl|…}} / collocation {{coi|pl|…}} / nyms {{syn|pl|…}}
      ====Declension==== / ====Conjugation====   (L4, or L5 under Etymology N)
      ====Usage notes====
      ====Synonyms==== / Antonyms / Hypernyms / Hyponyms / Meronyms / Holonyms
      ====Coordinate terms==== / ====Collocations====
      ====Derived terms==== / ====Related terms====     ({{col|pl|…}}, {{pl-derived verbs}})
      ====Descendants====
      ====Alternative forms====
  ===Trivia=== / ===References=== / ===Further reading=== / ===Anagrams===
                                                 (language-level, after the etymologies)
```

- **R5.1** Preserve the etymology-group structure: a page like *zamek* has multiple
  `Etymology N` sections, each with its own POS entries. Do **not** flatten them into one
  bag of senses; senses must stay attached to their etymology.
- **R5.2** Support both L3 and L4 POS placement (with/without `Etymology N`), and
  POS-subsections at L4 or L5 accordingly. **Heading depth is not semantic**: attach a
  section by what its heading *is* (POS, POS-subsection, language-level), using depth
  only to find its parent.
- **R5.3** POS headings to recognize (English Wiktionary spelling): Noun, Proper noun,
  Verb, Adjective, Adverb, Pronoun, Numeral, Determiner, Preposition, Postposition,
  Conjunction, Particle, Interjection, Prefix, Suffix, Interfix, Infix, Letter, Symbol,
  Phrase, Prepositional phrase, Proverb, Idiom, Abbreviation, Initialism, Acronym,
  Contraction, Participle, Affix, Circumfix, Combining form, Diacritical mark,
  Punctuation mark, Syllable, Romanization. A heading that maps to neither a POS nor a
  known section is counted (as unhandled templates are, R4.6) and its content kept as
  raw text, never dropped.
- **R5.4** Sense lists nest (`#`, `##`, `#*`, `#:`); sub-senses must be represented as
  child senses, not flattened.
- **R5.5** Sections that belong to the language rather than a POS — `Alternative forms`
  and `Pronunciation` above the etymologies; `Trivia`, `References`, `Further reading`,
  `See also`, `Anagrams` after them — must be attached at the right level.
- **R5.6** `{{senseid|pl|…}}` anchors must be captured so external data can reference a
  specific sense stably.

## 6. Polish-specific data requirements

- **R6.1 — Nouns.** Gender **and animacy**: masculine personal / masculine animate /
  masculine inanimate / feminine / neuter; plus *virile* vs *nonvirile* plural agreement.
  Full declension: 7 cases (nom, gen, dat, acc, ins, loc, voc) × singular/plural, with
  alternative forms per cell (e.g. nom pl `profesorowie` / `profesorzy`) and
  defective/pluralia-tantum paradigms represented as *absent*, not as empty strings.
- **R6.2 — Verbs.** Aspect (imperfective / perfective / biaspectual) and the aspect
  partner. The full paradigm must include: infinitive; present (or perfective future)
  1/2/3 sg & pl; past by person × number × gender (singular m/f/n, plural
  virile/nonvirile); periphrastic future (both `będę robił` and `będę robić`);
  imperative; conditional (same gender split as the past); impersonal past
  (`-no`/`-to`); verbal noun (`-nie`/`-cie`); active adjectival participle; passive
  adjectival participle; contemporary adverbial participle (`-ąc`); anterior adverbial
  participle (`-wszy`). Also frequentative/iterative and reflexive `się` marking.
- **R6.3 — Adjectives.** Full declension (case × number × gender incl. virile/nonvirile),
  degree (positive / comparative / superlative), and non-comparable marking. Derived
  adverbs where the article links them.
- **R6.4 — Pronouns / numerals.** Their irregular paradigms, including collective
  numerals (`dwoje`, `pięcioro`) and the special numeral agreement patterns.
- **R6.5 — Pronunciation.** IPA, audio file names, rhymes, **syllabification** and
  homophones, from `{{pl-pr}}` (`Module:zlw-lch-IPA`) or a literal `{{IPA|pl|…}}`.
  `{{pl-pr}}` packs most of this into parameters — `a=` audio (with `<text:…>`
  modifiers), `hh=` homophones, and one parameter per **dialect** (`CD=`, `MD=`, `CGP=`,
  `zag=`, `krk=`, …) — so regional variants are captured as separate `Pronunciation`s
  tagged with their dialect. The parameter → dialect map is config (R10.5). The
  Middle Polish variant (`mp=`) is dropped per R6.6a.
- **R6.6 — Form-of entries.** A very large share of Polish pages are inflected forms
  whose only content is `{{inflection of|pl|lemma||gen|p}}`. These must parse into
  structured `form_of` links with the grammatical tags decoded, not a gloss string. One
  call can carry **several tag sets**: `;` separates sets and `//` joins alternatives,
  so `{{inflection of|pl|mama||gen|s|;|nom//acc//voc|p}}` is four (case, number) pairs —
  and these entries are then
  **folded into the lemma and not emitted** (R3.13a). Parsing them accurately still
  matters: they are the cross-check on, and the supplement to, the Lua-generated
  paradigms.
- **R6.6a — Middle Polish is dropped at extraction.** en.wiktionary records Middle Polish
  inside modern Polish entries as a label, not as its own language section, so excluding
  it is a filtering rule rather than a section rule:
  Decision 8 (§12): **nothing Middle Polish remains in the corpus.** On live pages it
  appears in at least six places, all of which are dropped:
  - **Senses** whose labels include `Middle Polish` (`{{lb|pl|Middle Polish}}`, also
    combined: `{{lb|pl|reflexive-się|Middle Polish}}`).
  - **POS entries** carried by a term-level `{{tlb|pl|Middle Polish}}` (alias of
    `{{term-label}}`), or whose senses are *all* dropped by the rule above.
  - **Pronunciations**: the `mp=` parameter of `{{pl-pr}}`, and any variant qualified
    `Middle Polish` (`{{a|Middle Polish}}`).
  - **Alternative forms** qualified Middle Polish (`{{alt|pl|dóbr||Middle Polish}}`).
  - **Declension tables** from Middle Polish templates (`{{pl-mid-decl-noun}}`,
    `Module:pl-mid-noun`).
  - **Reference groups** headed `Middle Polish:` under Further reading/References (links
    to the 16th/17th-century dictionaries, `{{R:pl:SXVI}}`, `{{R:pl:SXVII}}`).
  - Cascade like R3.13a: if every entry on a page is dropped, the page yields no `Word`.
  - Magnitude check: `Category:Middle Polish` had 3,964 members on 2026-10-11 — the
    page-touch count in `stats.json` should land near that.
  - **R6.6b** The label set is **config, not code** (R10.5): `drop_labels` defaults to
    `["Middle Polish"]` and matches label aliases/redirects, so re-including it is a
    one-line change. Old Polish needs no entry — it is a separate L2 section already
    excluded by R3.2.
  - **R6.6c** Everything dropped is **counted** in `stats.json` (senses, entries, pages,
    pronunciations, alternative forms, tables, references — by label and by kind). Deleting content from live articles is only safe if we can
    see how much we deleted; an unexpected jump means the label matcher is over-firing.
- **R6.7 — Labels.** `{{lb|pl|…}}` values (colloquial, dated, obsolete, vulgar,
  transitive, reflexive-się, …) become typed tags; unknown labels pass through as
  strings. **Dialect labels are very common** on Polish entries (`Chełmno-Dobrzyń`,
  `Far Masovian`, `Central Greater Poland`, town names such as `Krotoszyn`): each maps to
  `TAG_DIALECTAL` *plus* its literal name in `raw_tags`, so the region survives. Labels
  are matched after resolving the label module's aliases, not by literal string.
- **R6.8 — Etymology.** Both the rendered text *and* structured links: borrowed-from /
  inherited-from / derived-from with source language codes and source terms, cognates,
  Proto-Slavic reconstructions, compound decomposition (`{{af|pl|…|-ka}}`).
- **R6.9 — Examples & quotations.** `{{ux|pl|…}}` / `{{uxi|pl|…}}` (Polish text +
  English translation), `{{quote-book}}`/`{{quote-journal}}`/`{{RQ:pl:…}}` with author,
  title, year, page, original text and translation kept separate.
- **R6.10 — Categories.** Both explicit `[[Category:…]]` and those emitted by templates
  during expansion (topical categories like *pl:Birds* are the useful ones).
- **R6.11 — Government (valency).** `{{+obj|pl|…}}` on a sense states what case or
  preposition the word governs (`:za(acc)`, `acc<what>`, `:do(gen)<to what>`). It is
  structured data — case enum, optional preposition, gloss of the slot — and must be
  captured per sense, not left in the gloss text.
- **R6.12 — Collocations.** `{{coi|pl|…}}` lines under a sense and the
  `====Collocations====` section carry a Polish phrase and its translation; they are kept
  as typed examples (collocation kind), sense-scoped where they appear under a sense.

## 7. Output format

- **R7.1** Protocol Buffers, **proto3**, schema versioned in `proto/polwikt.proto`;
  generated `*_pb2.py`/`*_pb2.pyi` are committed, and CI fails if they are stale.
- **R7.2** Storage: length-delimited (varint-prefixed) `Word` records, zstd-compressed,
  sharded (`words-00000-of-00064.pb.zst`). A single monolithic message is forbidden —
  the corpus must stream. Provide a reader helper that yields `Word`s.
- **R7.3** A sidecar `index.sqlite` mapping title → shard + offset, and lemma → entry ids.
- **R7.4** A `Corpus` metadata message recording dump date, dump sha1, whether the dump
  was the pinned one (R2.1a), pipeline git revision, proto schema version, the active
  `drop_labels` set (R6.6b), generation timestamp, and counts. A consumer must be able to
  tell from the corpus alone what was excluded from it. It is written **out of band**, to
  `corpus.meta.pb` beside the shards, because the timestamp would otherwise break G5's
  byte-identical shards.
- **R7.5** A **JSON dump** (`--format=jsonl`) of the same messages via `MessageToJson`,
  for eyeballing and diffing. Protobuf is the contract; JSON is a view.
- **R7.6** Field numbering discipline: never reuse or renumber fields; `reserved` on
  removal. Unknown/unmapped data goes to explicit `repeated string raw_tags` /
  `raw_*` fields rather than being dropped. No `map<>` fields anywhere: their wire order
  is unspecified, which would break G5 (enforced by a schema test).
- **R7.6a — Both plain and marked-up text.** Every human-readable string (gloss,
  example, etymology, usage note) is stored **twice**: a plain-text form with links
  flattened to their display text, and either the rendered form with markup (`raw_*`) or
  a span list (`LinkSpan`) carrying the link targets. Plain text is what a consumer
  greps, embeds or shows; the spans are what makes glosses navigable. Offsets are
  **Unicode codepoints** into the plain string — a byte offset convention would be a
  standing bug source in Polish text.

### Schema shape

The contract is `proto/polwikt.proto`; this is the shape it implements, not a second copy
to keep in sync:

- `Word` (one per lemma page) → `EtymologyGroup` (one per `Etymology N`, or one for the
  whole section) → `PosEntry` → `Sense` (recursive `subsenses`) and a flat `Form` list.
- Page-level material (shared pronunciation, language-level sections) hangs off `Word`;
  POS-specific detail is a `oneof` of `NounInfo` / `VerbInfo` / `AdjectiveInfo`.
- Every message that carries labels has typed `tags` plus `raw_tags`; every message
  built from a template keeps the raw `TemplateCall` (R4.2.1).
- A table cell covering several cases (nom/acc) becomes one `Form` per case, so
  `GrammaticalTags` stays scalar and the list stays pivotable (R7.8).

- **R7.7** Grammatical tags are **enums**, not free strings, for the closed Polish
  categories (case, number, gender, animacy, person, tense, mood, aspect, degree). Any
  tag we cannot map keeps its literal string in `raw_tags` — losing data is worse than an
  untyped field.
- **R7.7a** The corpus holds **one `Word` per lemma page**, never per inflected form
  (R3.13a). Expect ~10^5 records (~101k Polish lemmas on 2026-10-11) — the surface-form →
  lemma mapping lives in `index.sqlite`.
- **R7.8** Forms are a **flat tagged list**, not a fixed 7×2 table message. Paradigms are
  irregular (defective nouns, alternative cells, virile/nonvirile) and a flat list with
  tags survives that; consumers can pivot it into a table.

## 8. Quality, testing, observability

- **R8.1** A **golden corpus** of ~50 hand-picked Polish pages checked into the repo
  (as raw wikitext + expected protobuf/JSON), covering: regular and irregular nouns of
  every gender/animacy class, pluralia tantum, imperfective/perfective verb pairs,
  reflexive verbs, irregular verbs (`być`, `iść`, `jeść`, `chcieć`), adjectives with
  comparatives, numerals, pronouns, participles, multi-etymology pages (`zamek`, `bez`,
  `piec`), inflected-form-only pages (`kotów`, and `mamy`, which folds into two lemmas),
  borrowed terms, multi-word phrases, dialect-heavy entries, and — as *negative* cases —
  a page with Middle Polish content in every R6.6a position (`dobry`: senses, an
  alternative form, `mp=`, a reference group), a page that is entirely Middle Polish
  (must yield no record; chosen at M3), and pages that are both a lemma and an inflected
  form (`bez`, `mieć`: keep only their lemma halves, per R3.13a).
  Fixtures are taken from the **pinned dump**, never the live wiki, so the golden set and
  `stats.json` always describe the same snapshot. Tests run against them without needing
  a dump.
- **R8.1a — Golden store snapshot.** Expanding a fixture needs the templates and Lua
  modules it reaches. The golden set therefore includes a committed, zstd-compressed
  SQLite store (`tests/golden/store.sqlite.zst`, in the R3.1 layout) holding the fixture
  pages plus exactly the Template/Module pages their expansion touched (R3.8a). It is
  regenerated by a tool, never edited by hand, and only when the pin moves or fixtures
  are added — so its git churn is bounded by pin moves.
- **R8.2** Unit tests per extractor module (sense parsing, declension parsing, etymology
  linking) with wikitext fixtures.
- **R8.3** Regression check: a `stats.json` diff between runs. It is **direction-aware**:
  a >1% drop in a coverage count (senses, forms, entries with inflection) or a >1% rise in
  a failure count (errors, unhandled templates, unresolved forms, Wikidata stubs hit) is a
  regression. CI has no dump, so CI gates the stats of the golden run; the full-run diff
  is a local `polwikt stats-diff old.json new.json` that must be clean (or explained) in
  any commit that changes extraction behaviour or moves the pin.
- **R8.4** Coverage metrics reported per run: % of Polish lemmas with ≥1 sense, % of
  nouns with a declension, % of verbs with a conjugation, % of pages with pronunciation,
  count of unhandled templates, count of form pages folded vs. unresolved (R3.13c).
  Targets for v1: senses ≥99%, noun declension ≥95% of lemma nouns, verb conjugation ≥90%
  of lemma verbs.
- **R8.5** Structured logging with per-pass timing; `--limit N` and `--pages TITLE,…` for
  debugging a single article end-to-end, printing the expanded wikitext and node tree.

## 9. Performance & operational requirements

**Dev machine (measured 2026-08-22):** 2 cores, 5 GB RAM (~4 GB usable), project dir on
an 800 GB share with 63 GB free — but `/` has only **6.8 GB** free. **The targets below
are set for this box** (decision 9, §12): full runs happen here, at `--jobs 2`. Two
operational consequences that are *not* optional:
- **Everything large stays inside the project share.** `data/`, the page store, shard
  output — and also `TMPDIR`/`SQLITE_TMPDIR`, which SQLite and decompression otherwise
  point at `/tmp` on the 6.8 GB root filesystem. A P1 run that spills to `/tmp` will fill
  the root fs.
- **Memory, not cores, is the binding constraint here.** With ~4 GB usable, the R9.3
  per-worker budget is what keeps `--jobs 2` viable; a regression there stops the run
  outright rather than just slowing it.


- **R9.1** P1 (full dump scan) target: ≤ 60 min on this box (`lbzcat` uses both cores
  for decompression; the XML parse is the single-threaded part). It runs once per dump.
- **R9.2** P3 (extraction over all ~1.8×10^5 Polish pages) target: **≤ 2 h at
  `--jobs 2`**, provisional — it is reset from the throughput M4 measures
  (pages/sec/worker), and the measured number replaces this one. Most pages are short
  form-of entries; the cost is in the ~10^5 lemmas that expand Lua tables. `--pages` /
  `--limit` runs finish in seconds; the full run is not part of the edit loop.
- **R9.3** Peak RSS **≤ 1.5 GB per worker**, so two workers plus the parent fit in the
  ~4 GB usable. The pipeline must not require the whole corpus in memory at any point —
  P4's folding and linking work through SQLite, not in-memory dicts of every word.
- **R9.4** Resumable: each pass checkpoints; interrupting and re-running skips completed
  work.
- **R9.5** Disk budget documented (dump + page store + subset + output). Target total
  ≤ 60 GB, to fit the 63 GB available on the project share. The pinned dump itself is
  ~1.65 GB compressed (`enwiktionary-20261001-pages-articles.xml.bz2`), and R2.4 forbids
  ever holding it decompressed on disk. `pages.sqlite` stores bodies uncompressed (R3.1);
  its real size is measured at M2.

## 10. Implementation constraints

- **R10.1** Python 3.13, pinned in `.python-version` and installed by uv (the system
  interpreter is not used). Type-annotated; `mypy --strict` on the pipeline package.
- **R10.2** Dependencies kept minimal and pinned: `wikitextprocessor`, `lupa` (Lua),
  `protobuf`, `zstandard`, `click` for the CLI, `pytest`/`mypy`/`ruff` for dev.
  `wiktextract` is a **dev/test-only** dependency (the cross-check oracle of §12.1),
  never imported by the pipeline at runtime.
  - **`wikitextprocessor` and `wiktextract` are installed from git at exact commit SHAs,
    not from PyPI.** Their published releases (0.4.96 / 1.99.7) are years stale and expose
    the old pickle `cache_file` API; the SQLite `Wtp(db_path=…)` + `process_dump()` design
    this spec assumes exists only on git main. The two move in lockstep, so an upgrade
    bumps both SHAs in one commit, re-locks, and re-runs the golden suite.
  - Dependency resolution is `uv` with a committed `uv.lock`; CI installs `--locked`.
    Dev tools and the oracle live in a PEP 735 `dev` dependency group, so they never
    appear in the package's install requirements. `make` wraps the uv commands.
- **R10.3** CLI shape:
  ```
  polwikt scan     --dump enwiktionary-*.xml.bz2 --db pages.sqlite
  polwikt extract  --db pages.sqlite --out out/ --jobs 2 [--limit N] [--pages …]
  polwikt finalize --in out/ --out polwikt.pb.zst
  polwikt inspect  <title>            # human-readable dump of one entry
  polwikt stats-diff old.json new.json   # R8.3 regression check
  ```
  plus `polwikt run` to chain all passes. `polwikt subset` stays as a stub while P2 is
  deferred (§3).
- **R10.4** Package layout: `polwikt/{dump,subset,expand,parse,extract/{noun,verb,adj,
  etymology,pronunciation,sense},proto,cli}` (`subset/` stays an empty stub while P2 is
  deferred). Polish-specific knowledge lives under
  `extract/`, so the engine layer stays language-agnostic for a possible future language.
- **R10.5** Configuration (POS heading map, label→tag map, section name map,
  template policy, `drop_labels`, the dump pin) lives in **data files** (TOML/YAML/JSON),
  not hardcoded in Python, so Wiktionary convention changes — and scope changes like
  re-including Middle Polish — don't need code edits.

## 12. Decisions & open questions

All ten are **settled**: 1–5 when the spec was written, 6–10 in the 2026-10-11 review.
Kept here as the record of what was decided and why.

1. ~~Build on wikitextprocessor, or wrap wiktextract's English extractor?~~
   **Decided: own extractor on `wikitextprocessor`.** We use it for the dump store,
   template/Lua expansion and the `WikiNode` parse tree, and write all Polish extraction
   ourselves — full control over the proto and over Polish-specific detail
   (etymology grouping, animacy, paradigm cells) that wiktextract's JSON flattens away.
   `wiktextract` is still installed as a **cross-check oracle**: its JSON for the golden
   corpus (R8.1) is generated and diffed against ours, so divergences surface as a
   deliberate decision rather than an unnoticed bug.
2. ~~Keep inflected-form pages as full records, or fold them into the lemma?~~
   **Decided: fold and drop** (R3.13a–c). Inflected-form entries never become `Word`
   records; what they carry that the lemma's paradigm lacks is merged into the lemma's
   forms, and the surface-form → lemma mapping survives in `index.sqlite`. Folding is
   per POS entry, so pages that are simultaneously a lemma and a form keep their lemma
   half. Unresolvable form pages are counted and logged rather than dropped quietly.
3. ~~How much rendered text do we keep alongside the structured data?~~
   **Decided: keep both** (R7.6a). Each human-readable string is stored as plain text
   *and* with its markup/link targets — glosses get a `LinkSpan` list over codepoint
   offsets, longer prose keeps a `raw_*` twin. Consumers that want a string get one;
   consumers that want to follow `[[kot]]` can.
4. ~~Dump cadence: pin one, or track `latest`?~~ **Decided: pin one** (R2.1a).
   `dump_date` + `dump_sha1` live in `polwikt.toml`; moving the pin is its own commit
   with the `stats.json` diff reviewed alongside it, so Wiktionary churn never mixes with
   our own changes in a regression diff.
5. ~~Is Old Polish in scope?~~ **Decided: out of scope.** `==Old Polish==` (`zlw-opl`)
   is a separate L2 language section on en.wiktionary, so the P1 filter (R3.2) excludes
   it for free: a page with only an Old Polish section is never stored, and on a page
   that has both, only the `==Polish==` section is read. Adding it later is a change to
   the language-heading config (R10.5), not to the pipeline.
   - *Middle* Polish is **also dropped, at extraction** (R6.6a–c). It is not a separate
     section — en.wiktionary marks it with `{{lb|pl|Middle Polish}}` on senses inside
     modern Polish entries — so it is filtered by label, cascading sense → entry → page,
     with every drop counted in `stats.json`. `drop_labels` in the config reverses it.
6. ~~Keep P2 (static template/module closure → `subset.sqlite`)?~~ **Decided: defer.**
   P1's ns-0 filter already makes the store Polish-only; Lua computes `require` targets at
   runtime, so a static closure needs a fallback to the full store anyway; and
   `--pages`/`--limit` already give the fast loop. P3 reads `pages.sqlite` directly, and
   expansion records what it touches (R3.8a). P2 returns only if M2 measures the store too
   big for page cache.
7. ~~Where do golden fixtures and their template/module dependencies come from?~~
   **Decided: a snapshot of the pinned dump** (R8.1, R8.1a). Fixture pages plus exactly
   the templates/modules their expansion touched, committed as one compressed store and
   regenerated only with the pin. Live-wiki fixtures were rejected: they drift from the
   pin, and Special:Export does not follow Lua `require`.
8. ~~How far does the Middle Polish drop extend?~~ **Decided: all of it** (R6.6a) —
   senses, entries, `mp=` pronunciations, qualified alternative forms, Middle Polish
   declension tables and the Middle Polish reference groups, each counted by kind.
9. ~~Which machine are the performance targets for?~~ **Decided: this 2-core / 5 GB box**
   (§9). R9.2/R9.3 are restated for `--jobs 2`; the P3 wall-clock target is reset from
   M4's measured throughput.
10. ~~Fold participle entries into their verb, or keep them?~~ **Decided: keep them as
    records** (R3.13a). Adjectival participle entries (`pieczony`, `czytający`) carry
    their own full adjectival declension and sometimes lexicalised senses (`zakochany`
    "in love"); folding them into one verb `Form` would lose both. They stay `Word`
    records linked to the verb, and the verb's participle `Form` points at them.
    Indeclinable adverbial participles (`czytając`, `przeczytawszy`) have no paradigm
    of their own and fold like any other inflected form.
